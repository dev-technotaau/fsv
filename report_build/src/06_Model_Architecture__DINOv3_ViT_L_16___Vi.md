# AREA: Model Architecture (DINOv3 ViT-L/16 + ViT-Adapter + MSDeform + Mask2Former + UNet3+ refinement)

## SUMMARY
The production segmentation model is a 6-stage pipeline defined in training/model.py and training/vit_adapter.py: a frozen-pretrained DINOv3 ViT-L/16 backbone (facebook/dinov3-vitl16-pretrain-lvd1689m, hidden dim 1024, patch 16, 24 transformer blocks, 4 register tokens) with last-6-block weighted-sum aggregation; a ViT-Adapter (Spatial Prior Module CNN + 4 bidirectional deformable interaction stages) producing a 4-scale pyramid; a 12-layer Multi-Scale Deformable-Attention pixel decoder; a 15-layer Mask2Former-style transformer decoder with 64 queries, masked cross-attention and CLS+register global-token memory; and a UNet3+-style refinement head (96 channels, 4 blocks, edge/distance/CGM/PointRend sub-heads) run for 3 iterations, optionally cued by a frozen Intel/dpt-hybrid-midas depth teacher. The active configs (configs/phase1.yaml at 512px, configs/phase2.yaml at 1024px) drive every value; decoder_dim=512, num_queries=64, num_layers=15, pixel_decoder_layers=12/ffn=3072. The H+ (vith16plus, ~840M) variant is the *default* in code/config.py but is NOT used in production — both phase YAMLs explicitly select ViT-L. Total/trainable param count is computed at runtime in train.py (not hardcoded); the only "485M" figure lives in phase1.yaml optimizer comments as an engineer's estimate of the trainable count.

## NARRATIVE
## Model architecture: how the fence segmenter is actually built

The whole network lives in two files — `training/model.py` (1,835 lines) and `training/vit_adapter.py` (467 lines) — and is assembled by `FenceSegmentationModel` from whatever `ModelConfig` the active YAML provides. Both production phases (`configs/phase1.yaml`, `configs/phase2.yaml`) select the **DINOv3 ViT-L/16** backbone, `facebook/dinov3-vitl16-pretrain-lvd1689m`. It's worth nailing this down because the *dataclass default* in `training/config.py:26` is actually the bigger H+ model (`dinov3-vith16plus-pretrain-lvd1689m`, ~840M), and the phase1 header comment even talks about "DINOv3 H+". But that is a leftover narrative — the operative `backbone_name:` line in both YAMLs (phase1 line 13, phase2 line 13) is ViT-L. H+ only ever shows up as a "drop to this if VRAM-limited" fallback note and as the config default. So: production is ViT-L (~300M), period.

### 1. The backbone (DINOv3 ViT-L/16)

`DinoBackbone` (model.py:44) is a thin wrapper over HuggingFace `AutoModel`. It reads `hidden_size` (1024 for ViT-L) into `self.dim`, auto-detects `patch_size` (16 for DINOv3, 14 for DINOv2), and reads `num_register_tokens` — DINOv3 ships with **4 register tokens** sitting between the CLS token and the patch tokens, so the model always slices off `skip = 1 + 4 = 5` leading tokens before reshaping patches back to a spatial grid (model.py:214).

Two DINOv3-specific tricks are wired in. First, `drop_path_rate` is pushed into the HF config (0.1 in phase1, 0.05 in phase2). Second, and more importantly, **multi-block aggregation**: instead of taking only the final transformer block's output, the model fuses the last *N* blocks' patch tokens. Both phases set `multi_block_n: 6` with `aggregation_type: "weighted_sum"` — a set of 6 learnable scalars, initialized to zeros and softmax-normalized at every forward (model.py:118-122, 222-225), so at init it's a plain average and the model learns which of the last 6 layers matter for dense prediction. (The phase1 line-19 comment says "rolled back from 6," but the live value is 6.) `backbone_freeze_first_n_layers` is 0 everywhere, so the entire backbone trains end-to-end, just at a much lower LR than the heads.

### 2. The ViT-Adapter

A plain ViT only emits one coarse feature scale (stride 16). For pixel-accurate fence masks you need a real multi-scale pyramid, so the model uses the **ViT-Adapter** recipe (Chen et al., ICLR 2023), enabled via `use_vit_adapter: true` in both phases. When it's on, `DinoBackboneWithAdapter` (model.py:272) takes over and drives the backbone block-by-block instead of in one HF call.

It has three moving parts, all in `vit_adapter.py`:

- **Spatial Prior Module** (SPM, line 245): a small ResNet-ish CNN running in parallel to the ViT, taking the raw RGB. Channels grow `3 -> 64 -> 128 -> 256 -> 256` (with `inplanes=64`), producing four maps at strides 4/8/16/32, each then 1x1-projected up to the backbone dim (1024). These are `c1..c4`.
- **Injector** (line 308): at each interaction stage, the ViT patch tokens (queries) pull detail from the pyramid (c2/c3/c4, three levels) via deformable cross-attention, added back through a per-channel LayerScale `gamma` that starts at `init_values=0.0` — i.e. zero injection at init, so the pretrained ViT is undisturbed and the adapter ramps in gradually.
- **Extractor** (line 346): the reverse direction — the pyramid tokens (queries) attend back to the single-scale ViT features and get a small FFN mix (expansion ratio `ffn_ratio=0.25`, so the hidden width is ~256 for ViT-L).

These are paired into an `InteractionBlock` that always runs Extractor-then-Injector (matching the official implementation). There are `n_interactions=4` of them, spaced evenly across depth: `step = n_blocks // 4`, indexes `[(i+1)*step-1]`. For ViT-L's 24 blocks that's `[5, 11, 17, 23]`. Deformable attention uses `n_heads=8`, `n_points=4`. The whole MSDeformAttn op is a pure-PyTorch `grid_sample` implementation (`_ms_deform_attn`, line 45) — no custom CUDA kernel to compile, which is why it runs anywhere.

After the last block, the ViT's stride-16 spatial features are LayerNorm'd and residually added into the pyramid's c3 (also stride 16) — fusing global ViT reasoning with the detail-rich CNN pyramid at a matched scale (model.py:508-517). The output pyramid is `{res2: stride4, res3: stride8, res4: stride16 (fused), res5: stride32}`, all at dim 1024, which then get 1x1-projected down to `decoder_dim=512`.

### 3. The MSDeform pixel decoder

`MSDeformPixelDecoder` (model.py:618) is the real Mask2Former pixel decoder, implemented by wrapping HuggingFace's `Mask2FormerPixelDecoderEncoderLayer`. Both phases run `pixel_decoder_layers: 12`, `heads: 8`, `ffn_dim: 3072` (the config.py defaults are a much lighter 6 layers / 1024 ffn). It operates on exactly **three** scales — res3, res4, res5 — because `n_levels=3` and `n_points=4` are hardcoded inside the HF layer. Each forward builds 2D sinusoidal position encodings and normalized reference points, adds a learnable per-scale `level_embed` (3×dim, init std 0.02), and stacks the 12 deformable-attention encoder layers over the flattened concatenation of the three scales. The high-resolution `res2` output is reconstructed as `res2_lateral + upsample(enhanced res3)` followed by a 3×3 smooth conv. That res2 map becomes the per-pixel mask embedding; res3/res4/res5 become the transformer decoder's cross-attention memory.

### 4. The Mask2Former-style transformer decoder

`Mask2FormerLikeDecoder` (model.py:827) is where the actual mask queries live: `decoder_dim=512`, **64 learnable queries**, **15 decoder layers**, 8 heads, dropout 0. (Again, much bigger than config.py's defaults of 256/16/6.) Each layer is masked-cross-attention → query self-attention → FFN. Masks are predicted per query by an einsum dot-product between query embeddings and the res2 pixel features, then aggregated into a single fence-vs-background logit via a softmax over a per-query class head.

The two defining Mask2Former features are both on. **Masked attention** (`use_masked_attention: true`, threshold 0.5): each layer downsamples the previous layer's predicted masks to the current memory resolution, thresholds them in logit space (threshold 0.5 → logit 0), and blocks each query from attending outside its own predicted region. There's a NaN-safety guard that re-opens all positions if a query's row would be fully masked. **Global tokens** (`use_global_tokens: true`): the CLS token plus the 4 register tokens are projected to 512-d, LayerNorm'd, and appended to every layer's memory as always-attended global context. The decoder also emits **16 mask predictions** (a step-0 prediction before any layer plus one after each of the 15 layers) for deep supervision, and cycles the three memory scales across layers (`scale_idx = layer_index % 3`).

### 5. The UNet3+ refinement head

The coarse decoder mask is upsampled to full resolution and handed to a learnable **UNet3+ refinement head** (`RefinementHead`, model.py:1080), run for **3 iterations**. It's configured with `refinement_channels=96`, `num_blocks=4`. The encoder is a 5-scale UNet with channels `96 -> 192 -> 384 -> 768 -> 1536`; the decoder has 4 nodes (D0..D3) all kept at a uniform 96-channel width, and each decoder node receives full-scale skips from every shallower-or-equal encoder scale, every deeper decoder node, and the bottleneck — the UNet3+ "full-scale skip" design that's good for thin structures like fence pickets.

Its input is `RGB(3) + coarse_mask(1) + extras`. The extras are: 64 channels projected from the pixel-decoder features via a *learnable* 1×1 conv (there's an explicit code note that this conv was previously frozen by accident inside a `no_grad` block and is now called outside it), plus a free `y_coord` channel (normalized vertical position, since sky is up and ground is down), plus 1 depth channel — so 66 extra channels with depth on.

The head carries a small zoo of auxiliary heads, all configured on in both phases: an **edge head** (Sobel-supervised), a **signed-distance regression head**, the **Full-scale Deep Supervision** side heads off D1..D3 (3 heads), a **Classification-Guided Module** (CGM) — a pooled binary "does this image contain any fence?" classifier off the bottleneck (`AdaptiveAvgPool → Linear(1536→384) → GELU → Dropout(0.5) → Linear(384→1)`), and a forward-time **PointRend** module that re-predicts the K=4096 most-uncertain pixels through a 3-layer MLP (`Linear(c+1→128)→GELU→Linear(128→128)→GELU→Linear(128→1)`). The refined output is computed as a residual in logit space: `logit(coarse) + residual`, then PointRend-refined. Critically, the CGM gate (`logits += log(sigmoid(cgm))`, which multiplicatively suppresses predictions on no-fence images) is applied **only at inference**, never during training; during training the CGM is supervised independently. Between refinement iterations the previous output is detached, bounding gradient depth.

### 6. The depth teacher

When `refinement_use_depth: true` (on in both phases), the head loads **Intel/dpt-hybrid-midas**, freezes it (`requires_grad=False`, `eval()`), and computes a per-pixel relative-depth map under `no_grad`: un-normalize the ImageNet-normalized input, re-normalize to DPT's mean/std=0.5, resize to 384×384, run DPT, upsample back, and min-max normalize to [0,1]. There's a deliberate `train()` override on the whole model that re-snaps the DPT to eval on every mode flip, specifically to stop its BatchNorm running-stats from drifting over a multi-day run.

### Gradient checkpointing and params

Both phases set `gradient_checkpointing: true`. `enable_gradient_checkpointing()` turns on HF's backbone checkpointing *and* flips an `_extra_checkpointing` flag so the pixel decoder, transformer decoder, and each refinement iteration get wrapped in `torch.utils.checkpoint(use_reentrant=False)` during training. There is no hardcoded parameter count anywhere in the model — `train.py` (lines 844-849) computes total and trainable counts at runtime via `sum(p.numel())`. The "~485M trainable" figure the client may have seen exists only as an engineer's annotation in the phase1 optimizer comments (lines 120-122), used to justify LR choices; it should be treated as an estimate of the ViT-L + 15-layer decoder + 3-iter refinement trainable count, not a verified measured value.

### Phase 1 vs Phase 2

The architecture is byte-for-byte identical across phases — that's intentional, so phase 2 can warm-start from phase 1's best checkpoint (`init_from: outputs/training_v2/phase1/checkpoints/best.pt`). What changes is the regimen: phase 1 trains at **512px** on the full split for 120 epochs (base_lr 1.5e-4, backbone_lr 1.5e-5, plain AdamW); phase 2 fine-tunes at **1024px** on the HQ subset for 70 epochs with a lower LR (7.5e-5 / 3.0e-6), AdamW8bit to save VRAM, gentler augmentation, drop_path dropped to 0.05, and EMA self-distillation turned on. The boundary kernel widens (5→7) and the distance-clip widens (50→80px) to suit the higher resolution.
