# AREA: tools/ utility scripts (dataset, ONNX export, eval, split/manifest builders, occluder pool, PII/license audit, SWA, golden set, md-to-pdf, Gemini trial)

## SUMMARY
The tools/ directory is the operational backbone of the Fence Stain Simulator project: 15 standalone, well-documented Python CLIs that sit between the labeling pipeline and the deployed ONNX model. They cover dataset construction (build_mask_splits, build_hq_final, split_masks, standardize_images), training-data assembly (dataset.py with its augmentation stack and occluder pool), evaluation and analysis (eval_checkpoint, analyze_eval), final-model production (swa_average, export_onnx), governance/compliance (scan_pii, audit_licenses, select_golden_set), the client deliverable (md_to_pdf), and a one-off research probe (trial_gemini3_vs_current). The crown jewel is export_onnx.py, which wraps the trained DINOv3 checkpoint into a single-input/single-output ONNX graph at opset 17 with temperature baked in, a 5e-3 parity check, an fp16/int8 variant path, and a fully self-describing sidecar JSON. All scripts are CURRENT and in active use; dataset.py and export_onnx.py both show as locally modified in git status. One concrete stale artifact: md_to_pdf.py's embedded SVG flowchart still says "DINOv2-Small ~31M params," which contradicts the production DINOv3 ViT-L model.

## NARRATIVE
## The tools/ subsystem — how raw data becomes a shippable model

The `tools/` directory is where the project's day-to-day operational work happens. Everything between "we have a pile of labeled images" and "we have an ONNX file the browser can run" is a script in here. There are fifteen of them, and they're unusually clean: every one has a real module docstring with a quick-start command, sensible argparse defaults, atomic writes (`tmp` + `os.replace`) so a killed job never leaves a half-written split, and dry-run flags on the destructive ones. This is clearly code that's been run many times in anger, not throwaway glue.

### The dataset layer (dataset.py)

`tools/dataset.py` is the largest and most important file (1,455 lines). It defines `FenceDataset`, which reads two parallel JSONL files — the image split (e.g. `train.jsonl`) and a mask split (`train_masks.jsonl`) — and joins them on the `id` key. The mask decoding logic is the load-bearing detail: masks on disk are tri-class (0 = background, 1 = visible fence, 2 = occluder in front of the fence), and the dataset deliberately treats class 2 as background (`mask == 1`), with a legacy fallback to `mask > 0` for old binary {0,255} masks. The docstring is candid that a previous version used `mask > 0` unconditionally and was silently folding occluders into the fence class — about a 20% systematic mislabel on images with annotated occluders. That's the kind of bug that quietly caps a model's ceiling, and it's now fixed.

The augmentation stack is genuinely fence-specific rather than generic. Phase 1 (512px) is aggressive: a `OneOf` "distance scaling" block that either zooms in, shrinks-and-reflect-pads (to simulate a far-away fence), or does a boundary-aware crop centered on a fence edge (so the gradient budget is spent where the model actually learns — fence-vs-grass, fence-vs-sky); then geometric ops, harsh-sun/shadow/flare lighting, strong color jitter (p=0.85, to break the model's reliance on "brown = fence"), blur/noise/JPEG degradation, and three occlusion mechanisms. Two of those are custom Albumentations `DualTransform`s: `CopyPasteOccluder` pastes RGBA cutouts (foliage, people, vehicles) and *carves the GT mask* wherever the occluder is opaque (alpha ≥ 0.5), so the augmented image matches the labeling convention; and `HardNegativeWoodPaste` pastes wooden non-fence objects into background only, mask unchanged, to teach "wood texture alone is not a fence." Phase 2 (1024px fine-tune) is much gentler to preserve fine detail. Per-sample loss weighting by review provenance is supported (manual=1.0, auto_accept=0.85, auto_clear=0.95, unreviewed=0.5). There's also a correctness-critical `seed_worker` that re-seeds numpy per DataLoader worker — without it every worker would inherit the same RNG and the effective augmentation variety would shrink by a factor of num_workers.

`verify_split_integrity()` is the safety net: it confirms every image has a mask row, that train/val/test don't share IDs within a phase, and — importantly — it *warns loudly* (rather than silently passing) if the Phase-1 train set overlaps Phase-2 `val_hq`/`test_hq`, because that would inflate the headline number after a multi-day run.

### Building the splits and manifests

A small family of scripts builds the JSONLs the dataset consumes. `build_mask_splits.py` walks each image split and emits a parallel `*_masks.jsonl`, pulling the final class from `manifest_final.jsonl` and the per-image review provenance from `annotations_v1/manual_review.jsonl`, collapsing it into a single `review_source` label. `build_hq_final.py` and `standardize_images.py` both derive the high-resolution subset for Phase-2 fine-tuning, and they do it the right way: rather than re-stratifying the HQ images independently (which could put a high-res copy of a scene in train and a low-res copy in test), they filter the *existing* full splits down to rows whose shorter edge clears the threshold (default 1024px). HQ images therefore stay on the same side of the train/test boundary as their siblings. `standardize_images.py` additionally tags every row with a resolution tier (ULTRA ≥2048, HD 1536-2047, STANDARD 1024-1535, LOW 800-1023) and writes a resolution report; it's the earlier-stage cousin of `build_hq_final.py` and there's some intentional overlap between the two. `split_masks.py` is a pure filesystem helper that hard-links mask PNGs into per-split directories (zero extra disk via `os.link`, falling back to copy across volumes). All of these lock the `test` outputs read-only (chmod 0o444) so the held-out set can't be accidentally clobbered.

`build_occluder_pool.py` is the supplier for the augmentation occluders. It has three composable modes: a dependency-free procedural foliage/branch generator (~200 PNGs of anti-aliased ellipse clusters with feathered alpha), a COCO-2017 extractor that auto-downloads the val annotations (~240MB, cached) and cuts out 17 curated categories (person, car, dog, potted_plant, …) using their built-in polygon masks, and a rembg path for the user's own stock photos. A separate `--wooden-negatives` mode procedurally generates planks, garden beds, and deck patches with drawn wood grain for the hard-negative paste.

### Evaluation, analysis, and final-model production

`eval_checkpoint.py` runs a checkpoint over any split with optional multi-scale + horizontal-flip TTA and the full post-processing chain (morphology, guided filter, DenseCRF, connected-component cleanup), writing both an aggregate `eval_summary.json` and a per-image `eval_per_image.jsonl`. `analyze_eval.py` then slices those per-image rows by subcategory, review source, and class — reporting IoU mean/median/std and the 10th-percentile tail — so you can see exactly which subset (say, `occlusion_mild`) is dragging the average down, and it can diff two runs head-to-head on shared image IDs.

`swa_average.py` produces the actual shippable weights. It element-wise averages N checkpoints (only floating tensors; BN counters and other integer buffers are kept from the first checkpoint), and — a nice touch — it carries forward the post-training calibration (temperature, per-subcategory thresholds, binarize threshold) from whichever source looks most "post-trained," preferring `best.pt`, then `best_inference.pt`, then `latest.pt`. Without that inheritance the averaged model would silently lose its calibration.

### The deployment bridge: export_onnx.py

This is the script the client report should dwell on, because it's the seam between training and the browser/server. It loads the checkpoint (preferring the config bundled inside the `.pt`), wraps the model in an `_OnnxWrapper` that exposes a single tensor output, and — critically — *bakes temperature scaling into the graph itself*: the wrapper returns `sigmoid(logits.float() / T)`, with T read from the checkpoint meta (default 1.0). The deployed model is therefore self-calibrating; the sidecar flags `temperature_baked_in: True` so client code knows not to re-apply it. By default it exports the refined-head output (production quality, ~6MB larger and ~10ms slower than the coarse Mask2Former mask). The export uses opset 17 (the docstring notes 14+ is enough for ViT, but 17 is chosen for safety), constant folding on, and a fixed batch of 1 unless `--dynamic-batch` is passed. The input contract is explicit: (1,3,H,W) fp32, ImageNet-normalized RGB; output is (1,1,H,W) sigmoid probabilities in [0,1]. Image size is snapped to a multiple of the patch size.

After export it validates parity: it runs the same random input through the PyTorch wrapper and through onnxruntime (CPU provider) and asserts the max absolute difference is within **5e-3** — it warns rather than fails if exceeded, on the theory that ViT + bilinear interpolation can drift slightly. Optional fp16 (via `onnxconverter_common.float16`, keeping fp32 I/O) and int8 dynamic quantization (`onnxruntime.quantization`, QUInt8) variants are each re-validated against the fp32 PyTorch reference with looser tolerances (1e-2 and 5e-2 respectively). Every variant gets its own sidecar `.json` that is essentially a complete deployment spec: input/output names, shapes, dtype, normalization constants, opset, file size, the full training config and provenance, suggested post-processing parameters, exporter library versions, the parity-check result, the calibration block, and the training run's final test metrics. That sidecar is what makes the ONNX file genuinely portable.

### Governance, the golden set, and the client deliverable

Three scripts exist purely for due diligence. `scan_pii.py` runs Google Vision face detection (defaulting to the rows likely to contain people plus a 5% sample, since most fence photos are empty yards) and writes a GDPR/CCPA report flagging "significant" faces (≥2% of image area, ≥0.5 confidence). `audit_licenses.py` buckets every source into SAFE (Pexels/Unsplash/Pixabay), SAFE_ATTR (Wikimedia/Flickr CC-BY), or RISKY (Reddit, Pinterest, Houzz, the search-engine scrapes, company sites) and can emit a legally-clean `manifest_safe.jsonl`; it SHA-256-hashes the manifest for an audit trail. `select_golden_set.py` carves out a ~100-image stratified, seed-stable benchmark from the *test* split for a senior annotator to hand-mask, used as the auto-label quality gate (target IoU > 0.70), the inter-annotator agreement target (> 0.90), and the deployment sign-off floor.

`md_to_pdf.py` is the mechanism behind this very report family — it renders `PROJECT_WORKFLOW.md` into a branded HTML + PDF via headless Chrome/Edge, replacing the ASCII flow diagram with a hand-built SVG. Worth flagging: that embedded SVG still labels the model "DINOv2-Small ~31M params," which is stale relative to the production DINOv3 backbone and should be corrected before the PDF goes out.

Finally, `trial_gemini3_vs_current.py` is the odd one out — a single-image research probe that calls Gemini 3.0 Flash via Vertex AI, refines its polygons with Shapely, and measures *agreement* (not accuracy — it's careful to say there's no human ground truth for the trial image) against the current Grounded-SAM 2 mask. It's experimental and outside the production pipeline.

## UNCERTAINTIES

So H+ is NOT merely an unused fallback comment — it is the literal code default. If a checkpoint failed to expose patch_size the export would snap image_size to the wrong multiple. Could not verify whether the production checkpoint exposes patch_size=16 (model.py auto-detects it, so it likely does, but unconfirmed here).
