# AREA: Data refining (validate/clean/catalog) + stratified train/val/test split (Steps 2-3)

## SUMMARY
prepare_dataset.py is the Step-2 "refine/catalog" stage: it parallel-decodes every scraped image (positives in data_scraped/, negatives in data_scraped_neg/), SHA-256-hashes the actual file bytes, detects orphans, removes any positive that collides by SHA with a negative (cross-set dedup deletes FROM positives, keeping the neg copy as the more-trustworthy label), tags each surviving image with a keyword-derived subcategory, and writes dataset/manifest.jsonl plus integrity.json and removed.jsonl. The actual run scanned 33,674 files, found 0 corrupt/0 orphan-files, removed exactly 251 cross-set duplicates, and emitted a 33,423-row manifest. split_dataset.py is the Step-3 stratified splitter: stratified by (class x subcategory), seed 42, 70/15/15, with a BK-tree/union-find dhash near-duplicate grouping pass (threshold 5 hamming) so visually-similar images never straddle splits, and it marks test.jsonl read-only. The committed split (built from manifest_final.jsonl) is train 23,394 / val 5,013 / test 5,016 = 33,423. dataset/splits_smoke/ is a tiny 30/10/10 toy split used to smoke-test the downstream pipeline, not for training.

## NARRATIVE
## Step 2 - Refining, validating and cataloguing the scraped corpus

Everything in this stage hangs off a single, fairly disciplined script, `prepare_dataset.py`. Its job is to take the two raw scrape folders - `data_scraped/` (positives: wooden fences we want the model to learn) and `data_scraped_neg/` (negatives: everything that looks fence-ish but isn't a stainable wooden fence) - and turn them into one trustworthy `manifest.jsonl` that the rest of the pipeline can rely on. The header comment is upfront that this is "Phase 1+2 of the data pipeline," and the design choices show someone who has been burned by bad data before.

The integrity check is the heart of it. For every file it runs four escalating tests in a worker process (`_verify_file`, lines 281-319): `stat()` the file (catches a path that's gone), reject zero-byte files, compute a full SHA-256 over the *actual bytes* in 1 MiB chunks (deliberately not trusting any sha that might already be in the metadata - "don't trust metadata's sha - catches corruption"), then `PIL.Image.verify()` for a cheap truncation check, and finally a full `im.load()` to confirm the pixels actually decode. A nice detail at line 42: `ImageFile.LOAD_TRUNCATED_IMAGES = False` is set explicitly, so a half-downloaded JPEG fails the check instead of silently sneaking through as a half-grey image. The whole thing runs across a `ProcessPoolExecutor` (default workers = CPU count minus two), and if you Ctrl-C it, it throws away partial results and returns exit 130 rather than writing a half-baked manifest.

Two kinds of "orphan" are detected: a file on disk with no metadata row, and a metadata row pointing at a file that isn't there. Only orphan *files* are candidates for deletion; orphan *metadata* is reported but left alone. On the real run none of this mattered - the report shows `orphan_files_pos: 0`, `orphan_files_neg: 0`, and just `orphan_metadata_pos: 9` (nine stray metadata rows on the positive side, no files deleted for it).

The most interesting decision is the **cross-set SHA dedup**, and the direction matters. The script builds a set of every negative's SHA-256, then finds any *positive* whose byte-hash collides with a negative and removes it **from the positive set, keeping the negative copy** (lines 455-459, 494-497). The reasoning is spelled out in the comment at lines 450-454: when a stock-photo API serves a loose match, or when a non-wood fence got mislabelled as a positive, the negative-side label is almost always the more accurate one - so the script trusts the negative classification and drops the positive. On the actual run this removed exactly **251** images, and `removed.jsonl` confirms every single one of those 251 lines carries the reason `cross-set-dup` - there were zero integrity failures and zero orphan-file deletions. The very first entries are `company_sites__fenceanddecksupply_com__*.jpg`, which fits the "company site image also scraped into negatives" story.

The cataloguing side is the subcategory taxonomy (lines 53-252). Each image is bucketed by first-match-wins keyword search over its original `query` text. The module docstring claims "18 pos + 10 neg cats," but that line is stale - the actual tables contain **30 positive rule rows resolving to 26 unique positive labels** and **19 negative rule rows / 19 unique negative labels**. The ordering is deliberate: hard-positive buckets like `motion_focus`, `lighting`, `angle`, `occlusion`, `staining_process`, `damaged_construction` are listed first so a specifically-described shot lands in its proper bucket, and only the plain "cedar fence" / "wooden" / "fence" queries fall through to the generic `style_cedar` / `fence_general_wood` / `fence_general` catch-alls at the bottom (lines 170-174). Anything that matches nothing gets the fallback `general_positive` or `negative_uncategorized`. The manifest row itself is built conservatively: it starts from the *complete* original metadata row (preserving dhash, source, origin URLs, per-source license fields), then layers on a fresh `uuid4` id, `class`, `subcategory`, and crucially *overwrites* width/height/bytes/sha256 with the disk-verified values from the integrity pass (lines 493-521).

There are two optional knobs the report should call out. `--reclassify-nonwood-as-neg` is a label-only move that shifts `pos:style_nonwood` rows into `neg:neg_nonwood_fence` without touching files - explicitly recommended for a cedar-staining model where vinyl/metal fences shouldn't count as positives. `--subsample-pure-random N` deterministically keeps only N of the huge `neg_pure_random` bucket (seed 42) and drops the rest at the manifest level - a way to stop the easy "random internet photo" negatives from drowning out the hard negatives. On the original `prepare_dataset` run neither was applied (`transforms: {}`), but the gap between the original manifest and the manifest that was actually split tells us the nonwood reclassification *was* applied later (see below).

The accompanying audit reports round out Step 2. `resolution_report.json` catalogs all 33,423 images into resolution tiers - ULTRA (>=2048px, 1,286), HD (1,536-2,047, 6,260), STANDARD (1,024-1,535, 13,154), LOW (800-1,023, 12,723) - and defines an HQ subset of everything with a shorter edge >= 1024px, which is **20,700 images (13,977 pos / 6,723 neg, 61.9% of the set)** earmarked for the Phase-2 1024px fine-tune. `LICENSE_AUDIT.md` / `licenses_per_source.json` sort every source into SAFE / SAFE_ATTR / RISKY: **12,367 SAFE (37%)**, **3,519 SAFE_ATTR (Wikimedia, attribution required, 10.5%)**, and **17,537 RISKY (52.5%)** scraped from Google/Bing/Houzz/Pinterest/company sites. The audit recommends training the deliverable on the **15,886 SAFE+SAFE_ATTR** subset, which is exactly the row count of `manifest_safe.jsonl`. Finally, `suspect_pos_samples_for_manual_review.csv` lists **103** auto-accepted positives whose generated masks cover essentially nothing (coverage around 0.0001-0.0006%, 1-4 fence pixels) - a targeted QA list for catching empty/false-positive masks before they poison training.

## Step 3 - The stratified, leak-proof split

`split_dataset.py` takes the manifest and produces `train.jsonl` / `val.jsonl` / `test.jsonl` plus a `split_info.json` audit file. It stratifies by `(class, subcategory)` so every bucket is proportionally represented in all three splits, at the default **70/15/15** ratio with **seed 42**. Two engineering details make it trustworthy. First, it replaces Python's randomized `hash()` with a `stable_hash32` based on SHA-256 (lines 74-79), and derives each stratum's shuffle seed from `seed XOR stable_hash32("class||subcat")` - so the same `--seed` reproduces the identical split on any machine, any Python version, regardless of PYTHONHASHSEED. Second, and this is the part clients care about, it has a **dhash near-duplicate grouping** pass (`--group-by-dhash`). It clusters images whose perceptual dhash is within a hamming distance of 5 - first unioning exact-dhash matches, then a BK-tree hamming search for near matches, all stitched together with a union-find - and treats each cluster as a single atomic "bucket" that must go entirely into one split. This is what prevents the classic disaster where near-identical photos end up in both train and test and inflate the score.

Before anything is written, `verify_split` asserts two things that "cannot silently fail": the three splits sum exactly to the input row count, and the train/val/test id-sets are pairwise disjoint (zero leakage). The test set is then `chmod`-ed to `0o444` read-only so nobody accidentally overwrites the held-out set; the writer clears that read-only bit on a deliberate re-run so the guard doesn't break reproducibility.

The committed `split_info.json` records exactly how the live split was produced, and it's worth being precise: the command was `split_dataset.py --manifest dataset/manifest_final.jsonl --force --group-by-dhash` - note it ran on **manifest_final.jsonl**, not the original manifest. That `_final` manifest is the one where the non-wood reclassification was applied, which is why in the split distribution `pos:style_nonwood` has collapsed to just 3 rows while a `neg:style_nonwood` bucket of 1,786 has appeared. The dhash pass found 32,898 unique groups out of 33,423 rows, 227 of which span more than one row (covering 752 rows total, largest cluster 152 images). The final, verified totals are **train 23,394 / val 5,013 / test 5,016**, summing to the full **33,423** - and those numbers match the raw `wc -l` line counts of the three files exactly. Actual ratios came out 0.6999 / 0.1500 / 0.1501. Three tiny strata (neg:multi_structure n=2, neg:urban_rundown n=1, neg:weather_extreme n=1) fell under the min-group-size of 3 and were dumped wholesale into train with a warning, as designed. A parallel set of HQ splits also exists - train_hq 14,529 / val_hq 3,087 / test_hq 3,084 - for the high-resolution fine-tune phase.

## Smoke split vs real split

`dataset/splits_smoke/` is not a real dataset. It is a deliberately tiny **30 / 10 / 10** row split (confirmed by line count) carrying the exact same file family as the real directory - `train/val/test.jsonl`, plus the `_hq` and `_masks` variants - and the rows have the identical 20-field schema (class, subcategory, dhash, sha256, etc.). Its purpose is to let the downstream training/annotation code be exercised end-to-end in seconds without loading the full 33k-image manifest. It was created 2026-05-02, well after the real split (2026-04-26), and should be treated as a developer smoke-test artifact, never as training data.
