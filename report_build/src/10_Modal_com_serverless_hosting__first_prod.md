# AREA: Modal.com serverless hosting (first production host) for ONNX fence-segmentation inference

## SUMMARY
Modal.com is the first serverless production host for the Fence Stain Simulator's server-side ONNX inference. The browser stays a static page (HF Static Space) and only uploads a fence photo via multipart POST to a Modal-hosted FastAPI /detect endpoint, which runs the ONNX model and returns a compact grayscale PNG mask; all recoloring/post-processing stays in the browser. There are two Modal apps: app.py is the older DINOv2-small model (518x518, CPU, ~135 MB ONNX, app name "f-stain-inference") and app_dinov3.py is the flagship DINOv3-L model (512x512, T4 GPU, ~2.47 GB external-data ONNX, app name "f-stain-dinov3-inference"). local_server.py is an identical-protocol localhost:8001 FastAPI server for testing the DINOv3 ONNX on the developer's own GPU without a Modal redeploy, and diagnose_mask.py is a standalone CLI that replays the full browser pipeline against the DINOv2 ONNX to find which post-processing filter is killing a detection. app_dinov3.py and local_server.py are the CURRENT production/dev path; app.py and diagnose_mask.py are the older DINOv2-era code.

## NARRATIVE
## Modal.com serverless hosting

Modal is the first place this project actually put a model on a server. Up to that point the whole thing was client-side: the browser downloaded the ONNX file (a 135 MB DINOv2 model in the early days) and ran inference locally with onnxruntime-web, which meant every visitor paid a ~22-second download before they could do anything. The Modal subsystem flips that around. The web page stays a dumb static asset on a Hugging Face Static Space; the only thing that changes is that the "load the model" step is replaced by an HTTP call. The browser uploads a photo, Modal runs the model and hands back a small PNG mask, and all the fun interactive stuff (color picker, opacity, blend modes, connected-component cleanup, vegetation filtering) still happens locally in JavaScript so changing the stain colour never touches the network. The README sketches this as a two-box diagram and quotes "first result in ~2-3 seconds instead of waiting 22s."

### Two apps, two eras

There are two distinct Modal applications in `modal_inference/`, and the distinction matters a lot for the report.

`app.py` is the original. It hosts the DINOv2-small model. The Modal app is named `f-stain-inference`, the input size is 518x518 (snapped to DINOv2's patch size of 14), and the model file is `fence_model_dinov2.onnx` baked straight into the container image. This runs on **CPU only** — `cpu=2.0`, `memory=2048` — because DINOv2-small is light enough that two cores handle it comfortably (the code even sets `intra_op_num_threads = 2`). The container image is a `debian_slim` Python 3.11 base with a tight, fully-pinned dependency set: onnxruntime 1.20.0, pillow 10.4.0, numpy 1.26.4, fastapi 0.115.6, python-multipart 0.0.20. The model is bundled into the image via `.add_local_file` so cold starts don't have to download weights separately.

`app_dinov3.py` is the current flagship. It hosts the big two-phase model — DINOv3-L backbone with a ViT-Adapter, MSDeform attention, a Mask2Former head and a refinement head on top. It's deployed under a different app name, `f-stain-dinov3-inference`, deliberately so it gets its own URL and doesn't disturb the older DINOv2 endpoint while it's being shaken out (the module docstring spells this rationale out). The input size drops to 512 (DINOv3 uses patch size 16, and 512 = 32×16). The model is far heavier — the graph file is ~13.9 MB but it references an external-data file of ~2.45 GB, because the full weight set blows past ONNX's 2 GB protobuf limit, so the weights live in `fence_dinov3_phase1.onnx.data`. Both files get uploaded into the image. The code's comment of "2.47 GB" matches the on-disk total.

Because the DINOv3 model is so much bigger, `app_dinov3.py` runs on a **T4 GPU** (`gpu="T4"`, 16 GB VRAM — Modal's cheapest GPU), with the CPU side bumped to 4 GB RAM purely for image decode and pre/post-processing. The scale-down window is also longer (600 s / 10 min vs 300 s / 5 min on the CPU app) and `max_containers` is lowered from 10 to 4, both because a GPU container is more expensive to spin up and to keep around.

### The CUDA bootstrapping saga

The single most interesting piece of engineering in this subsystem is how `app_dinov3.py` gets onnxruntime-gpu to actually use the GPU. Modal's `debian_slim` base plus a T4 gives you only the kernel driver, not the CUDA user-space libraries, and onnxruntime-gpu 1.24.4 needs CUDA 12 + cuDNN 9 shared objects at runtime to even create the CUDAExecutionProvider. So the image pip-installs seven NVIDIA wheels (cublas, cuda-runtime, cuda-nvrtc, cudnn pinned to 9.10.2.21 to match training, cufft, curand, nvjitlink) that ship the `.so` files under `site-packages/nvidia/<lib>/lib/`. Then there are two belt-and-braces tricks. First, `LD_LIBRARY_PATH` is set via `.env(...)` at container build/start time, not at runtime — the code comment is emphatic that doing `os.environ['LD_LIBRARY_PATH'] = ...` from inside Python is too late, because the dynamic linker reads it once when Python launches. Second, at import time it explicitly `ctypes.CDLL(..., RTLD_GLOBAL)`-loads eight critical libs (libcudart.so.12, libcublas/Lt.so.12, libcudnn.so.9, libcufft.so.11, libcurand.so.10, libnvJitLink.so.12, libnvrtc.so.12) so their symbols are globally visible when ORT's CUDA provider loads later. The whole startup block prints diagnostics — Python version, LD_LIBRARY_PATH, which nvidia .so files it found, dlopen OK/FAIL per lib, and `ort.get_available_providers()`. The comments note they were burned by this on the first deploy: without it, ORT silently falls back to CPU and runs ~25x slower. The session itself is created with `providers=["CUDAExecutionProvider", "CPUExecutionProvider"]` so CUDA is primary with a CPU safety net.

### The /detect endpoint and the sidecar-JSON parity

Both apps expose the same two routes wrapped in a FastAPI app via `@modal.asgi_app()`: `GET /` returns a small health JSON (`status`, `service`, `model_input_size`, `channel_order: RGB`, and on the DINOv3/local versions the active `providers`) and doubles as a wake-up ping the browser fires on page load to warm a cold container; `POST /detect` takes a multipart `image` field and returns a PNG. The session is loaded exactly once per container inside the asgi closure and reused across every request that container handles, with `@modal.concurrent(max_inputs=4)` letting one container serve four parallel requests.

Server-side preprocessing is deliberately identical across all three servers and is the crux of "sidecar JSON parity." The model has to be fed exactly what it was trained on or accuracy collapses: convert to RGB, resize to the model's square input with **bilinear** interpolation (a comment explicitly forbids nearest-neighbor "or accuracy degrades on small fences"), divide by 255, transpose HWC→CHW and add a batch axis to get NCHW `[1,3,S,S]` fp32, then normalize with the standard ImageNet mean `[0.485, 0.456, 0.406]` and std `[0.229, 0.224, 0.225]`. Those constants are duplicated verbatim in app.py, app_dinov3.py, local_server.py and diagnose_mask.py — that duplication is the parity contract: whatever the export's sidecar JSON declares for input size and normalization, every host hard-codes the same thing. One subtle but real difference: app.py hard-codes the ONNX I/O names `"input"`/`"output"`, whereas app_dinov3.py and local_server.py read them dynamically from the session (`get_inputs()[0].name` / `get_outputs()[0].name`) because the refined-head export names its output `mask_prob` rather than `output`.

The response is a compact grayscale PNG. The sigmoid probability map `(1,1,S,S)` is squeezed to 2-D, multiplied by 255, clipped and cast to uint8, wrapped as a PIL mode-"L" image and saved as PNG with `optimize=True, compress_level=6`. The README notes this lands around 30-100 KB versus ~1 MB for a raw float array, and accepts the ~0.4% (1/255) quantization loss as negligible against the browser's thresholds. The browser then decodes the PNG back to floats and runs its existing post-processing. Response headers carry `X-Inference-Ms` and `X-Upload-Bytes` for debugging (DINOv3/local add `X-Provider` so you can confirm CUDA vs CPU), plus `Cache-Control: no-cache, no-store`. Input is guarded: empty body → 400, over 20 MB → 413, undecodable image → 400.

### Scale-to-zero and warm-up

Both apps run `min_containers=0`, so when nobody's using the tool there are zero containers and zero cost — Modal's headline serverless behaviour. The trade-off is cold start: the first visitor after the idle window waits for a container to boot (and load the model). The mitigation is the GET `/` health ping the browser sends on page load, which starts a container warming in the background so that by the time the user clicks "Detect" the session is hot. The CPU app keeps a container alive 5 minutes past the last request; the GPU app keeps it 10 minutes, because a GPU cold start (including loading a 2.45 GB weights file) hurts more. The README documents an optional `min_containers=1` to eliminate cold starts entirely at roughly +$10/mo baseline, and a cost table built on Modal's ~$0.000056/sec CPU pricing showing the whole thing fits inside the $30/mo free credit for tens of thousands of inferences.

### local_server.py and diagnose_mask.py

`local_server.py` is the developer's local rehearsal of `app_dinov3.py`. It's a plain uvicorn FastAPI server on `0.0.0.0:8001` that loads `models/fence_dinov3_phase1.onnx` from disk and exposes the exact same `/detect` protocol, so you can point `index2_dinov3.html`'s `CONFIG.MODAL_ENDPOINT` at `http://localhost:8001/detect` and test a freshly-exported ONNX on your own GPU without paying the Modal redeploy round-trip. It has the Windows analogue of the CUDA-bootstrapping problem: before importing onnxruntime it walks `site-packages/nvidia/*/bin` and calls `os.add_dll_directory` so the CUDA DLLs are findable, and it loudly warns if CUDAExecutionProvider didn't come up ("~25 sec per image instead of ~1 sec"). This is current and is the inner-loop counterpart to the DINOv3 Modal app.

`diagnose_mask.py` is a different animal — a debugging tool, not a server. You run it as `python diagnose_mask.py <image>` and it answers the question "why didn't the stain show up for this photo?" It loads the **DINOv2** ONNX (518 input, CPU) and then faithfully replays the *entire* browser pipeline: it mirrors the browser's `imageToUploadBlob` (max-dim 1024 resize, saturate 1.06, contrast 1.12, 1.5/98.5 percentile auto-levels, JPEG round-trip at quality 85), runs the model, upsamples, then walks every post-processing stage with the browser's hard-coded thresholds (soft-mask LOW 0.72 / HIGH 0.88, CC area 2%, vegetation, sky, bark, trunk, CC colour-outlier, per-CC PCA axis filter, junk-blob, building filter) printing non-zero pixel counts at each step and pinpointing exactly which filter zeroed the mask, finishing with a side-by-side visualization. Because it's pinned to the DINOv2 model and 518 input, it belongs to the older era of the project.

### Currency verdict

Git status is the tiebreaker. `app.py` and `diagnose_mask.py` are committed and tied to the now-superseded DINOv2 model; the README documents only that DINOv2 flow and never mentions the DINOv3 app, so all three are effectively stale relative to production. `app_dinov3.py` and `local_server.py` are still untracked (`??` in git status) — they're the newer DINOv3 additions and represent the current production-and-dev inference path. For the client report, the live story is: Modal hosts the DINOv3-L flagship on a scale-to-zero T4 GPU container behind a FastAPI `/detect` endpoint, with the DINOv2 CPU app and the README as the historical first iteration.
