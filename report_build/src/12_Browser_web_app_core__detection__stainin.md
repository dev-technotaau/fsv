# AREA: Browser web app core (detection, staining, cleaning, preprocessing, passes, post-processing, WASM, WebGPU) — fence-staining-visualizer/index4_dinov3.html + wordpress/app.js

## SUMMARY
index4_dinov3.html (10,594 lines) is the current standalone single-page app for the Fence Stain Simulator. The browser never runs the segmentation model itself: it uploads a downscaled JPEG to a server /detect endpoint (a Google Cloud Run container, NOT Modal despite the variable name) and decodes the returned grayscale PNG mask, treating each pixel's value as the model's confidence (0-1). That confidence map then flows through a large client-side JavaScript pipeline — soft-mask thresholding, spatially-guided plank recovery, ~15 connected-component / color / shape "cleanup" filters, hole-fill and bottom-extend — before being used as the blending alpha for Apply Stain (recolorFence) or Clean Fence (cleanFence). A client-side OWL-ViT zero-shot object detector (Xenova/owlvit-base-patch32, ~80MB, in a Web Worker) acts as a fail-open pre-filter that blocks obvious non-fence photos. The heavy per-pixel math (dilate/erode, masked box blur, guided filter, sRGB↔Lab, alpha blend, soft-mask threshold) is accelerated by a hand-written WebAssembly module (fsv_postprocess_simd.wasm with SIMD128, scalar fsv_postprocess.wasm fallback), with WebGPU compute shaders as a secondary accelerator for large-radius dilate, and pure-JS fallbacks throughout. wordpress/app.js (207KB) is the byte-for-byte logical port of the same pipeline for WordPress embedding.

## NARRATIVE
## How the browser app actually works

The thing to understand first is that the web app is *thin on inference and thick on cleanup*. The browser never loads the segmentation network. When a user uploads a photo and clicks "Apply Stain", the page shrinks the photo, ships it to a server, gets back a small grayscale picture where bright = "this is fence, I'm confident" and dark = "not fence", and then spends the overwhelming majority of its code turning that confidence map into a clean, believable stained-fence image entirely in JavaScript (with WebAssembly and, occasionally, the GPU doing the number-crunching). The current standalone app is `index4_dinov3.html` (10,594 lines); the WordPress build `wordpress/app.js` is the same logic ported into a JS file.

### 1. Upload and client-side preprocessing

On upload (`handleImageFile`, line 4690) the app rejects anything over 10 MB, then keeps the original full-resolution image around for the final composite. When it's time to call the server, `imageToUploadBlob` (line 4996) downscales the photo so its longest side is at most `UPLOAD_MAX_DIM = 1024` px and re-encodes it as JPEG at quality `0.85`. Before encoding it can run a light enhancement: the default "mild" pass nudges contrast to 1.12 and saturation to 1.06 and then auto-levels using the 1.5th/98.5th percentiles; the "aggressive" pass (only used as a fallback later) pushes contrast to 1.35, saturation to 1.18, brightness down to 0.88 and auto-levels more tightly. This is deliberately modest — the goal is to help borderline photos detect, not to alter what the customer sees.

### 2. The /detect call and the cold-start warm-up

The endpoint is `CONFIG.MODAL_ENDPOINT = https://fsv-dinov3-467125191853.us-central1.run.app/detect` (line 2899). One thing the client report should get right: despite the variable being called "MODAL" and several comments referring to "Modal", this is a **Google Cloud Run** URL (`us-central1.run.app`). The naming is a historical leftover from an earlier Modal-hosted version. The request is a simple `multipart/form-data` POST with one field, `image`, containing the JPEG named `fence.jpg` (`_uploadAndInfer`, line 5063). The server replies with a 512×512 grayscale PNG (roughly 30–100 KB). The client decodes it with `createImageBitmap`, reads the red channel of each pixel, and divides by 255 to get a `Float32` probability in [0, 1]. It also reads an `X-Inference-Ms` header to log how long the server's own GPU work took.

Because Cloud Run scales to zero, the very first request can be slow while the container "wakes up". To hide this, `init()` (line 3931) fires a warm-up: it strips `/detect` off the endpoint and does a plain GET to the container root on page load. The comment (line 3928) notes this returns in ~100 ms when warm or wakes the container in ~3–5 s cold. If that health check fails, the user simply sees "Simulator is starting up — your first preview may take a moment." rather than an error.

### 3. Confidence as the blending alpha

This is the conceptual heart of the app. The returned mask isn't treated as a yes/no stencil — its grayscale value *is* the model's confidence, and that confidence is what eventually becomes the opacity of the stain at each pixel. `USE_SOFT_MASK` is `true` (line 2961). In `postprocessMask` (line 7944) the raw probabilities are run through a soft threshold: anything at or below `SOFT_MASK_LOW = 0.50` is forced to zero (kills foggy false detections), anything at or above `SOFT_MASK_HIGH = 0.85` keeps its full value, and the band in between gets a smooth ramp (`p * (p-low)/(high-low)`). The effect is a hand-painted-looking alpha channel: razor-sharp and opaque where the model is sure, gently feathered where it's uncertain, and clean everywhere else.

### 4. The post-processing passes (the "cleanup")

After thresholding, the confidence map goes through a long, ordered gauntlet of filters inside `postprocessMask`. The order matters and is roughly: upsample the 512px mask to image size (bilinear), soft-threshold, then **spatially-guided recovery** (find very-confident "core" fence at prob ≥ 0.85, dilate that core by ~20 px to define a "fence zone", and inside that zone only, re-admit weaker pixels down to 0.40 — this recovers shadowed or oddly-lit planks without inviting false positives elsewhere). Then connected-component cleanup drops isolated blobs smaller than 0.05% of the image (a deliberately low floor, because the DINOv3-L model produces more fragmented predictions than the old DINOv2 model). Then a stack of appearance-based filters, each targeting a specific failure mode: a vegetation/green filter (`filterVegetation`, line 7902 — drops pixels where green beats both red and blue by more than 25, i.e. leaves), a sky filter (bright + low-saturation pixels in the top 40% of the frame), an adaptive bark filter, an adaptive trunk/off-color filter (compares each pixel to the fence's own mean color), a brick/red-masonry filter, a per-connected-component color-outlier filter, a second recovery pass that re-admits weathered pixels adjacent to surviving fence, then building/barn filters (which drop whole components whose mean confidence or saturation is far below the strongest fence component), hole-fill (fills small interior gaps like knots/nail-heads, capped at 0.3% area so picket gaps survive), and finally a small bottom-extension to recover the low-confidence kickboard at the base of planks. Two of these filters — orientation and per-CC principal-axis — are present but **disabled** (lines 3263, 3303) because they were carving real fence structure out in practice.

A nice engineering detail: all the pixel-radius and pixel-count knobs are auto-scaled (`_scalePostprocessOpts`, line 5121) to the capped 1536 px working resolution — radii linearly, areas quadratically — so a 20 px dilate behaves the same regardless of the source photo's megapixels. The final mask is then upsampled back to the original resolution before staining.

If the first detection comes back empty, `detectFence` (line 5967) runs a cascade of up to five passes: the same output re-run with progressively looser thresholds (free, no new server call), then one aggressive-preprocess re-upload (a second server call), and finally a multi-scale **tiled** inference (3×2, 4×3, 5×4 grids) for small or distant fences, gated and shape-checked so a deck or wall doesn't sneak through. The comment caps it at two server calls per Apply Stain (line 5055).

### 5. Apply Stain — recolorFence

`previewStain` (line 4585) is what the "Apply Stain" button runs: gate-check the photo, detect if there's no cached mask, then call `recolorFence` (line 10190). Recolor first derives a near-binary alpha from the soft mask (`deriveRecolorAlpha`, line 9353): pixels with confidence ≥ `RECOLOR_FULL_ALPHA_THRESHOLD = 0.15` get alpha 1.0 and only the thin outer fringe keeps a ramp. This is the trick that makes the stain look *solid* — without it, a confident 0.85 pixel would still let 15% of the original weathered wood bleed through and the color would read weak. It computes the fence's mean lightness and saturation over confident pixels, then per pixel blends the chosen stain via `applyBlendMode` (line 10363). The default "smart" mode keeps the target stain's hue but lets each pixel's lightness and saturation vary around the fence means (texRangeL = 0.75, texRangeS = 0.55), so the result follows the wood grain instead of looking like flat paint. Other modes (multiply, overlay, screen, color) are available. Final per-pixel opacity = user's opacity slider × derived alpha. If the user already ran Clean Fence, the stain is applied on top of the cleaned wood (chained flow).

There are **19 stains in 3 categories** (line 3419): General (Leatherwood #8B572A, Oxford Brown, Redwood, Natural Cedar, Cedar Tone), Semi-transparent (Chestnut, Mahogany, Pecan, Sequoia, Walnut), and Semi-solid (Auburn, Barnwood, Black #1A1A1A, Cape Cod Gray, Chocolate, Eucalyptus, Palomino, Sable, Slate Gray). Default is Leatherwood.

### 6. Clean Fence — restoring weathered wood

`cleanFence` (line 9715) is the "pressure-wash" simulation. It caps work to 1536 px, then derives a per-image clean-wood reference color by averaging the Lab values of the brightest 35% of fence pixels (those are the sun-exposed, least-weathered planks); if that doesn't look enough like wood it falls back to fixed `CLEAN_CFG` targets (a* = 6.0, b* = 17.0). The cleaning is frequency-preserving: an edge-aware **guided filter** (epsilon 150, so it smooths dirt/algae blotches but respects plank boundaries) extracts the low-frequency color cast; a smaller-radius guided filter separates fine wood-grain texture, which is then sharpened back in (1.15×); a per-plank Lab "jitter" adds subtle board-to-board variation so it doesn't look painted; and a uniform L* lift (capped between −15 and +35) brightens the whole fence to the target while preserving its natural shadow/highlight variation. Output chroma is capped at 19.0 and near-white highlights (L* > 92) are skipped. The cleaned region is composited back onto the full-resolution original through the same feathered mask alpha used by staining, so non-fence pixels stay sharp. The result is cached so a subsequent Apply Stain works on the restored wood.

### 7. WebAssembly

The per-pixel math is the bottleneck, so the heavy loops are implemented in C (`wasm/fsv_postprocess.c`) and compiled to two artifacts: `fsv_postprocess_simd.wasm` (19,725 bytes, SIMD128) and a scalar `fsv_postprocess.wasm` (9,668 bytes). At startup `_wasmInit` (line 8595) validates a 31-byte SIMD probe via `WebAssembly.validate`; if SIMD is supported it loads the SIMD build, otherwise the scalar one. Because emscripten minifies export names, the loader reads the sibling `.symbols` file to map original names (`fsv_dilate`, etc.) back to the minified exports, and manually runs the C static initializers and the sRGB LUT init since it bypasses emscripten's JS glue. The WASM ops are: sliding-window dilate/erode (O(N) monotonic-deque), masked box blur (double-precision integral images), batched sRGB↔Lab, the full guided-filter pipeline in one call, feathered alpha-blend, and the soft-mask threshold. SIMD (`wasm_f32x4_*`, `wasm_v128_bitselect`) is used in the pixelwise diff/mul, the soft-mask threshold, and the alpha blend. Every WASM call is wrapped in try/catch that, on failure, marks WASM unavailable and falls back to an equivalent optimized JS implementation — so the app degrades gracefully and never breaks.

### 8. WebGPU

WebGPU is a narrower, secondary accelerator. There is exactly one compute shader (`_GPU_DILATE_WGSL`, line 8975): a separable two-pass max-filter dilate with an 8×8 workgroup. `dilateAccelerated` (line 9102) only reaches for the GPU when WASM is unavailable *and* the dilate radius is ≥ 8 *and* the image is ≥ 250,000 pixels — i.e. exactly the large-radius recovery dilations where GPU parallelism pays off. The full fallback chain is WASM-SIMD → WASM-scalar → WebGPU → pure-JS `dilateFast`, and the comments assert the output is bit-identical across all four. All the other cleanup math (guided filter, Lab, blends, box blur) runs on WASM or JS, not the GPU.

### 9. The fence pre-filter gate (a second, separate model)

Before the server is ever called, the app runs a *client-side* zero-shot object detector as a cheap gate to block obvious non-fence uploads (selfies, food, a coffee cup on a wooden table). The model is **`Xenova/owlvit-base-patch32`** — OWL-ViT v1, ~80 MB — loaded into a Blob-URL Web Worker via transformers.js 3.0.2, preferring WebGPU/fp16 (3 retries) and falling back to WASM/q8. Note for the report: many code comments still say "OWLv2" or "SigLIP", but the model ID that's actually instantiated is `owlvit-base-patch32` (line 4108). The gate feeds eight "wooden fence" phrasings and eight distractor phrasings (stairs, deck, railing, etc.) in one pass and passes the image only if the best fence detection out-scores the best distractor by a small margin (SCORE_THRESHOLD 0.010, AREA_THRESHOLD 0.02, DISTRACTOR_AREA_MIN 0.10, COMPETITIVE_MARGIN 0.005). Crucially the gate is **fail-open**: any error returns "isFence: true", so a glitch in the gate never blocks a paying customer — the server detector has the final say.

### Download and reset
