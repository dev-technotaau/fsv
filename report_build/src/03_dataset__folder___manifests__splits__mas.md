# AREA: dataset/ folder — manifests, splits, mask sources, and supporting subsystems

## SUMMARY
The dataset/ folder is the source-of-truth control layer for the Ninja Fence Staining Visualizer's 33,423-image segmentation corpus. There are SIX manifest variants that form a clear lineage: manifest.jsonl (auto-labeled, 33,423 rows, pre-review class counts 21,414 pos / 12,009 neg) → manifest_final.jsonl (post-manual-review, SAME 33,423 rows but reclassified to 13,328 pos / 20,095 neg via the annotation pipeline) → manifest_hq_final.jsonl (the 20,700-row high-res subset). The CURRENT production training data are dataset/splits/*.jsonl (and *_hq.jsonl + *_masks.jsonl), which configs/phase1.yaml and phase2.yaml point to via splits_dir: "dataset/splits"; those splits were generated from manifest_final.jsonl (recorded in split_info.json). The pixel masks live in dataset/annotations_v1/masks/ (all 33,423 PNGs) and are wired into training through *_masks.jsonl. manifest.jsonl, manifest_hq.jsonl, manifest_safe.jsonl, the .bak files, integrity_DRYRUN.json, and several subdirs (training_set/, golden_set/, sam3_test/, trials/, finetune_runs/, splits_smoke/) are either superseded intermediates, legal/QA byproducts, or tooling fixtures — not the live training path.

## NARRATIVE
## The dataset/ folder: control plane for a 33,423-image fence corpus

If you only remember one thing about `dataset/`, make it this: the folder does **not** store the 23 GB of JPEGs themselves. Those live outside (`data_scraped/images/`, `data_scraped_neg/images/`) and are meant to be DVC-tracked. What `dataset/` holds is the *control plane* — the JSONL manifests, the train/val/test partitions, the pixel masks, the legal/QA audits, and the augmentation pools. Everything here is text or relatively small PNGs that define what the corpus *means* and exactly which bytes a given model was trained on. That is why there are so many similarly-named files: each one is a checkpoint in a multi-stage pipeline, and the team (sensibly) kept the intermediates and backups rather than overwriting in place.

### The manifest lineage (the part the client asked about)

There are six `manifest*.jsonl` files, and they are not redundant copies — they are a directed pipeline. The cleanest way to read them is left-to-right by processing stage.

**Stage 0 — raw curation.** `prepare_dataset.py` ingests ~60k scrape candidates, applies resolution/size/aspect filters, exact-SHA and near-duplicate (dhash, Hamming ≤ 5) dedup, and Google-Vision acceptance, then writes **`manifest.jsonl`** — 33,423 rows, 28.9 MB. At this stage the class labels are *auto-derived*: 21,414 positive (wood fence) and 12,009 negative. It also emits `manifest.jsonl.bak` (a literal safety copy — VERSIONING.md:192 says don't commit it), `removed.jsonl` (the 251 cross-set duplicate deletions, every row stamped `reason: cross-set-dup`), and `integrity.json`. There's a twin, `integrity_DRYRUN.json`, that is byte-for-byte identical to the real one except `removed_applied` is 0 instead of 251 and `dry_run` is true — it's the preview pass the engineer ran before committing to the deletions.

**Stage 1 — manual review and the great reclassification.** This is the most important and least obvious fact in the whole folder. The annotation pipeline (Grounding DINO → SAM 2 → priority fusion, documented in ANNOTATION_SYSTEM.md) wrote per-image masks and a running override log, `annotations_v1/manual_review.jsonl` (33,423 rows, append-only, last-write-wins). `annotation/export_final.py` then merges the immutable `manifest.jsonl` with that review log to produce **`manifest_final.jsonl`** — same 33,423 rows, but with two new fields (`class_source`, `original_class`) and a *dramatically* different class balance: **13,328 pos / 20,095 neg**. In other words, roughly 8,000 images that the auto-labeler called "fence" were demoted to negative by human review. Every row in `manifest_final` carries `class_source: manual_review`. If a client report quoted the old 21,414/12,009 numbers as the training composition, it would be wrong — `manifest_final.jsonl` is the real phase-1 source of truth.

**Stage 2 — resolution tiering.** Two parallel HQ subsets exist. `tools/standardize_images.py` produced **`manifest_hq.jsonl`** (20,700 rows ≥ 1024 px shorter edge) from the *pre-review* manifest — that one is now stale. `tools/build_hq_final.py` produced **`manifest_hq_final.jsonl`** (also 20,700 rows, but carrying the `class_source` corrections) from `manifest_final.jsonl`. The `_hq_final` file is the current phase-2 (1024 px fine-tune) manifest.

**Stage 2b — legal filtering (a side branch, not a successor).** `tools/audit_licenses.py --emit-safe` produced **`manifest_safe.jsonl`** (15,886 rows = the 12,367 SAFE + 3,519 SAFE_ATTR rows; the 17,537 RISKY rows are dropped). This is an optional commercial-deployment filter, not part of the current training path — current training still uses the full corpus.

So the "which one is current?" answer is: **`manifest_final.jsonl` (phase 1) and `manifest_hq_final.jsonl` (phase 2)** are the live manifests; `manifest.jsonl` is the immutable upstream baseline; `manifest_hq.jsonl` is superseded; `manifest_safe.jsonl` is a legal side-artifact; the two `.bak` files are backups.

### Where training actually reads from: splits/, not the manifests

Here is a subtle but critical point for the report. The training configs **do not name any `manifest_*` file**. `configs/phase1.yaml:190` and `configs/phase2.yaml:169` both set `splits_dir: "dataset/splits"`; phase 1 uses splits `train/val/test`, phase 2 uses `train_hq/val_hq/test_hq`. Those split JSONLs were generated by `split_dataset.py` *from* `manifest_final.jsonl` — and `dataset/splits/split_info.json` proves it: it records the command `split_dataset.py --manifest dataset/manifest_final.jsonl --force --group-by-dhash`, seed 42, the manifest SHA-256 (`2396de28…`), and the resulting counts. The actual split sizes on disk are **train 23,394 / val 5,013 / test 5,016** (70.0/15.0/15.0, dhash-group-aware so near-duplicates never straddle splits). Worth flagging: DATASHEET.md still quotes the older 23,397/5,011/5,015 numbers and the old class balance — that doc predates the final split and is stale.

The test splits are deliberately **chmod read-only** (`-r--r--r--` on `test.jsonl` and the `_hq` image splits) — a nice touch that physically prevents accidental test-set leakage.

### How masks get into training

The pixel labels live in **`dataset/annotations_v1/masks/`** — all 33,423 class-ID PNGs (plus an equal number of human-readable previews in `masks_preview/`). Training code never globs that directory directly. Instead `tools/build_mask_splits.py` emits parallel **`*_masks.jsonl`** files inside `dataset/splits/` (train_masks 23,394, val_masks 5,013, test_masks 5,016, and the `_hq` variants 14,529/3,087/3,084). Each row joins to the image split on `id` and carries `mask_path`, `class`, `class_source`, `fence_pixel_count`, `fence_coverage`, and review provenance. `tools/dataset.py` (the PyTorch `Dataset`) and `train_web_deployable.py` load the image split and the mask split together and join by id at runtime. Note the schema documents a 20-25 class taxonomy (ANNOTATION_CLASS_SCHEMA.md, classes 1/2/3 being the stainable wood-fence classes), but the training path collapses this — the recent commit "Fix tri-class mask decoding" indicates the model is trained on a tri-class (background / fence / occluder) reduction, and the mask splits themselves only record binary pos/neg.

### The supporting subdirectories

- **annotations_v1/** is the annotation engine's home: `results.jsonl` (169 MB raw auto-pipeline output, immutable), `results_final.jsonl` (auto+manual merged, 31.9 MB), `manual_review.jsonl` (the override log), two `.bak` variants, and a 389-row `qa_queue.jsonl`. This is current and central.
- **golden_set/** is a 100-image hand-masked benchmark, stratified across 20 subcategories, drawn from `test.jsonl` with seed 42 (selection_info.json records the source hash). Its README spells out the intended uses and IoU bars: >0.70 for auto-label acceptance, >0.90 for inter-annotator agreement. `images/` is intentionally empty (it points back at original paths). Current eval asset.
- **training_set/** is a tiny (100-image) fine-tune set wired into `annotation/finetune_dino_lora.py`. Its run dir, `finetune_runs/dino_lora_v1/training_log.jsonl`, is **0 bytes** — that LoRA experiment was scaffolded but never actually run.
- **hard_negatives/wood/** (200 PNGs) and **occluders/** (621 PNGs across 18 COCO categories + procedural foliage) are live *augmentation pools*, consumed by the `HardNegativeWoodPaste` and `CopyPasteOccluder` transforms in `tools/dataset.py`. The hard-negative pool is a thoughtful design choice: it pastes wooden non-fence objects into backgrounds so the model learns that "wood texture" alone is not "fence." The pools are built by `tools/build_occluder_pool.py`.
- **_coco_cache/** is just the one-time COCO 2017 download (a 253 MB zip + the val annotations + extracted images) that `build_occluder_pool.py` pulls cutouts from. Pure cache — regenerable, shouldn't be committed.
- **sam3_test/** (6 images) and **trials/gemini3_flash_vs_current/** (2 images) are throwaway experiments — a SAM 3 probe and a Gemini-3-Flash-vs-current mask A/B, respectively. Useful as evidence the team evaluated alternatives, but not part of the production data path.
- **splits_smoke/** mirrors the 12 split filenames at tiny scale (30/10/10 rows). Nothing in the codebase references it by path; it's a hand-built fixture for the `_smoke_*.py` dataloader sanity checks.

### Documentation

The Markdown files are genuinely good client-facing artifacts: DATASHEET.md (Gebru framework — but stale on counts), VERSIONING.md (DVC + tagging + disaster recovery), LICENSE_AUDIT.md (RISKY 52.5% / SAFE 37% / SAFE_ATTR 10.5%, with a clear "train on the 15,886 safe rows for commercial" recommendation), RESOLUTION_REPORT.md (the four tiers and the Phase-1-at-512 / Phase-2-at-1024 strategy), and the three ANNOTATION_* docs describing the taxonomy and review protocol. The newest file in the whole folder, `suspect_pos_samples_for_manual_review.csv` (May 14, 103 rows), is an active QA worklist flagging positives whose masks have near-zero fence pixels — a sign the team is still hunting label noise.

### One-line current-vs-stale verdict

Current training path: `manifest_final.jsonl` → `split_dataset.py` → `dataset/splits/{train,val,test}.jsonl` (+`_hq`, +`_masks`) → masks from `annotations_v1/masks/` → consumed by `tools/dataset.py` under `configs/phase1.yaml`/`phase2.yaml` on a DINOv3 ViT-L/16 backbone. Everything else is upstream baseline (`manifest.jsonl`), superseded intermediate (`manifest_hq.jsonl`), legal side-branch (`manifest_safe.jsonl`), backup (`.bak`), cache (`_coco_cache`), eval asset (`golden_set`), augmentation pool (`hard_negatives`, `occluders`), or throwaway experiment (`sam3_test`, `trials`, `splits_smoke`, the empty LoRA run).
