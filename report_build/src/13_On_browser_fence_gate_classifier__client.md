# AREA: On-browser fence-gate classifier (client-side OWL-ViT zero-shot pre-filter)

## SUMMARY
The fence-gate is a fully client-side, zero-shot object-detection pre-filter that runs in the browser before any image is sent to the server. It loads Xenova/owlvit-base-patch32 (OWL-ViT v1, ~80 MB quantized) through transformers.js v3.0.2 from the jsDelivr CDN inside a Blob-URL Web Worker, runs WebGPU-first with a WASM fallback, and decides whether an uploaded photo plausibly contains a wooden fence by comparing the best "fence" detection against the best "distractor" detection. If a fence does not clearly win, the upload is blocked with a friendly message and the server pipeline is never called. The gate is identical on both the Apply Stain (previewStain) and Clean Fence (cleanFence) paths, and is fail-open: any error returns isFence:true. The code is duplicated verbatim between fence-staining-visualizer/index4_dinov3.html and the WordPress mirror wordpress/app.js. The offline bake script and the fence_gate_text_features_v1.bin/.json files are obsolete leftovers from a previous SigLIP-based design and are no longer used or even runnable.

## NARRATIVE
## The browser-side fence gate

Before a single byte of an uploaded photo reaches the detection server, the app runs its own little AI model right inside the browser to answer one question: does this picture actually contain a wooden fence? This is the "fence gate." Its whole reason for existing is economic and experiential. The heavy lifting — fence segmentation — happens on a GPU-backed Cloud Run service (`https://fsv-dinov3-467125191853.us-central1.run.app/detect`, see line 2899 in both `index4_dinov3.html` and `wordpress/app.js`). Every call to that service costs money and takes time. If a visitor drops in a selfie, a plate of food, a screenshot, an interior shot, or a car, there is no point spending a GPU inference on it. The gate catches those uploads on the client and returns a friendly "No fence detected in this photo" message instead, so the server is only ever asked to work on images that plausibly have a fence in them.

The interesting design decision is that the gate uses *object detection*, not *image classification*. The code comments at lines 4015-4025 of `index4_dinov3.html` lay out the reasoning clearly, and it is worth repeating because it is genuinely the crux. A zero-shot classifier (the kind of thing CLIP or SigLIP does) scores the whole image against a text prompt. That works fine for "is this a dog or a cat," but it falls apart on the wood problem: a close-up of a wooden table, a wooden deck, or a coffee cup sitting on a wooden surface all light up the "wood" concept just as strongly as an actual fence does, because the whole-image signal is dominated by wood texture. There's no way to say "I want a fence that exists *as a locatable object* in the scene." Zero-shot *detection* fixes exactly that. The model has to draw a bounding box around the thing it found. A coffee cup on a wooden table has no fence to box; a small fence half-hidden behind pool umbrellas still produces a fence box even at 5% of the frame. That localization requirement is what lets the gate distinguish "fence in a busy scene" from "wood close-up."

### The model

The production model is `Xenova/owlvit-base-patch32` — OWL-ViT v1, base, patch-32 — declared as `MODEL_ID` at line 4108 (`index4_dinov3.html`) and line 758 (`wordpress/app.js`). It is loaded through transformers.js version 3.0.2, pulled at runtime from the jsDelivr CDN (`https://cdn.jsdelivr.net/npm/@huggingface/transformers@3.0.2`). It is roughly 80 MB quantized, downloaded once and then cached in IndexedDB by transformers.js, so repeat visitors get an effectively instant gate.

There's a clear paper trail showing this used to be OWLv2 base-ensemble (~150 MB) and was downgraded on purpose. The comment block at lines 4094-4107 spells out the tradeoff: OWL-ViT v1 at 768x768 produces 576 patch tokens versus OWLv2's 2304, roughly 4x less attention work, so WebGPU inference drops from ~7-9 s to ~2.5 s and the UI stops stuttering. The accuracy hit on complex scenes is acknowledged but judged irrelevant for a binary fence/not-fence call. (Note: several comments and console strings still say "SigLIP" or "OWLv2" — lines 3941, 4006, 4015, 4313, 4714 — these are stale wording, not stale behavior. The actual `MODEL_ID` is unambiguously OWL-ViT v1.)

### Worker architecture

The entire model — download, WebGPU initialization, and per-image inference — runs off the main thread in a Web Worker, so the page never freezes during the multi-second inference. The clever bit is how the worker is created: there is no separate `.js` file to ship. The worker body is written as a normal named function `_fenceGateWorkerFn` (line 4072), then at init time it is serialized with `.toString()`, wrapped in an IIFE, turned into a Blob, and a same-origin Blob URL is handed to `new Worker(url, { type: "module" })` (lines 4234-4237). Module-type is required so the worker can `import()` the transformers.js CDN bundle dynamically.

Image hand-off is built for speed. `_imageToGateInput` (line 4320) uses `createImageBitmap` with resize options to decode and downscale the photo to a 768px max dimension off the main thread (lines 4339-4349). That `ImageBitmap` is then transferred — not copied — to the worker via the postMessage transfer list `[bitmap]` (line 4442). Inside the worker, because transformers.js v3's `RawImage.read()` only reliably takes a URL string, the bitmap is drawn onto an `OffscreenCanvas`, converted to a JPEG blob at quality 0.9, and wrapped in an object URL that the pipeline fetches (lines 4155-4158). Both the bitmap and the URL are cleaned up in a `finally` block so nothing leaks. Communication between main thread and worker uses a small request/response protocol: every message carries an incrementing `_msgId`, and a `_pending` Map holds the per-request callbacks (`onProgress`, `onReady`, `onResult`, `onError`), demuxed by a single `onmessage` handler (lines 4248-4272).

### WebGPU first, WASM fallback

On init the worker tries WebGPU with fp16 precision, up to three times, backing off `attempt * 2000` ms between tries but only retrying on genuine network errors (the `isNet` regex matches fetch/network/connection/ECONNRESET/aborted/timeout). A non-network failure — e.g. the browser simply has no WebGPU — breaks the loop immediately without wasted retries (lines 4109-4131). If WebGPU never comes up, it falls back to the WASM backend with q8 (8-bit) quantization, and pins WASM to a single thread (`numThreads = 1`, line 4085) to avoid contention (lines 4132-4138). The device and dtype actually used are reported back and logged.

### The decision rule

This is where the fence-vs-distractor cleverness lives. Two query lists are fed to OWL-ViT in a single inference call. The eight *fence* queries are "wooden fence", "wood fence", "cedar fence", "wooden privacy fence", "wooden picket fence", "wooden plank fence", "stained wooden fence", "weathered wooden fence" (lines 4183-4192). The nine *distractor* queries are "wooden stairs", "wooden staircase", "wooden railing", "wooden banister", "wooden deck", "wooden balcony", "wooden floor", "wooden table", "wooden chair" (lines 4194-4210). There's an instructive note that "tree trunk" was removed from the distractors because it matched ~99% of the area on almost any outdoor scene with trees, which is common in legitimate fence photos, and was wrongly blocking real fences.

The model is queried with `{ threshold: 0.001, topk: 50, percentage: true }` (line 4439) — a deliberately near-zero threshold so the model returns essentially everything and the JavaScript does the real filtering. Four constants govern the verdict (lines 4498-4501): `SCORE_THRESHOLD = 0.010` (noise floor for any fence box), `AREA_THRESHOLD = 0.02` (a box must cover at least 2% of the image, killing one-pixel junk detections), `DISTRACTOR_AREA_MIN = 0.10` (distractors must cover at least 10% before they count — this stops small wooden elements like a hot-tub plank surround from spuriously beating a real fence), and `COMPETITIVE_MARGIN = 0.005` (the fence must beat the strongest distractor by this gap). The loop finds the best-scoring qualifying fence box and the best-scoring qualifying distractor box, and the final call is simply: `isFence = !!bestFence && bestFence.score > distractorScore + COMPETITIVE_MARGIN` (line 4540). The comment gives the concrete failure this fixed: wooden stairs were scoring 0.065 on "wooden fence," higher than a real fence's own 0.040, so no fixed threshold could separate them — but stairs score even higher on the "wooden stairs" query, so the *relative ranking* between buckets makes the correct call where an absolute threshold never could.

### Fail-open and identical on both buttons

The whole gate is fail-open by design. `_checkIsWoodenFence` has a `FAIL_OPEN(reason)` helper that returns `{ isFence: true, ... }`, used for no-image, gate-unavailable, image-conversion-error, and inference-error (lines 4371-4378, 4574-4576). If the worker can't be created or the model won't load, `status` becomes "unavailable" and the gate just waves everything through — the server-side detector remains the final authority. The philosophy stated in the comments is that the cost asymmetry favors letting things through: wrongly blocking a real fence is a lost sale, wrongly passing a non-fence is a fraction of a cent.

The gate runs identically on both user actions. `previewStain` (Apply Stain, line 4585) and `cleanFence` (Clean Fence, line 9715) both, when there's no cached mask yet, show "Checking image…", call `_checkIsWoodenFence` with the same progress handler, and on `!verdict.isFence` show the identical "No fence detected in this photo. Please upload a clear photo of a wooden fence." message and return before any server call (lines 4608-4615 and 9738-9745). The model is preloaded eagerly on page idle (`requestIdleCallback`, line 3954) and again fire-and-forget on every upload (line 4720), and `_initFenceGate` is idempotent via a status state machine plus a shared `loadPromise`, so all that eager loading never duplicates work.

### The obsolete SigLIP bake pipeline

There is a whole second, dead pipeline sitting in the tree. `scripts/bake_fence_gate_features.mjs` was built to precompute SigLIP text embeddings offline (`MODEL_ID = "Xenova/siglip-base-patch16-224"`, line 66) so the old *classification* gate wouldn't have to run a text encoder over ~56 prompts on first visit. It reads prompt arrays named `_FENCE_POSITIVE_PROMPTS` and `_FENCE_NEGATIVE_PROMPTS` out of the HTML (lines 99-100). Those arrays no longer exist — the live code uses `_FENCE_QUERIES`/`_FENCE_DISTRACTOR_QUERIES` — so `extractPrompts` would throw "not found in source" and the script can't even run. Its outputs, `fence_gate_text_features_v1.bin` (215,040 bytes = 70x768 float32) and `fence_gate_text_features_v1.json` (model siglip-base-patch16-224, promptCount 70, dim 768, baked 2026-06-08), still sit in both the root and `wordpress/` directories, but no runtime code references them. The script's `package.json` even pins a different transformers.js (`@xenova/transformers ^2.0.1`, v2) than the v3.0.2 the live gate loads. All of this — the bake script, its package files, node_modules, the cache, and the four feature files — should be treated as stale leftovers from the SigLIP era and are safe to ignore (or delete) without touching the working OWL-ViT gate. The `wordpress/app.js.bak` is an even older backup that predates the gate entirely.
