# AREA: Google Cloud Run GPU hosting (current production inference host)

## SUMMARY
The cloudrun_inference/ directory is the CURRENT production server-side inference host for the Fence Stain Simulator: a plain FastAPI + uvicorn container running the DINOv3 ViT-L/16 ONNX model on a single NVIDIA L4 GPU on Google Cloud Run. It exposes GET / (health + cold-instance wake) and POST /detect (multipart image upload, returns a 512x512 grayscale PNG mask). The model is baked into the image as two files — fence_dinov3_phase1.onnx (13,902,638 bytes / ~13.3 MB graph) plus fence_dinov3_phase1.onnx.data (2,451,570,688 bytes / ~2.28 GiB / 2.45 GB external weights). It is deployed with scale-to-zero (min-instances 0, max-instances 1), 16Gi memory, 4 CPU, concurrency 4, region us-central1, gen2, no-cpu-throttling, timeout 300s. Because it scales to zero, the first request after idle pays a cold start of roughly 30-60s while the GPU instance boots and the 2.45 GB model loads into VRAM — this is the crux of the client's 24/7-warm cost question.

## NARRATIVE
## Google Cloud Run GPU hosting — the current production inference host\n\nThe `cloudrun_inference/` directory is where the live, server-side brain of the Fence Stain Simulator runs today. When a visitor uploads a fence photo in the browser, the heavy lifting — running the DINOv3 segmentation model to find the fence — does not happen in their browser. It happens here, in a container on Google Cloud Run, on a single NVIDIA L4 GPU. The browser simply POSTs the photo up, waits, and gets back a grayscale mask image telling it exactly which pixels are fence.\n\n### What the service actually is\n\nUnder the hood this is deliberately boring and robust: a plain FastAPI application served by uvicorn inside a Docker container. There is no exotic framework. The whole server is a single file, `app.py`, about 250 lines. It exposes exactly two endpoints. `GET /` is a health check that returns a small JSON blob (`status: ok`, the model input size, channel order, and which ONNX execution providers are active). That endpoint does double duty as a *wake* call — the front-end pings it on page load so the GPU instance starts warming up in the background before the user ever clicks \"Apply Stain.\" The real work happens at `POST /detect`, which accepts a multipart `image` field, runs the model, and streams back a 512x512 PNG mask where each pixel's brightness (0-255) is the model's confidence that the pixel is fence (it's literally `sigmoid_probability * 255`).\n\nThe model itself is the flagship: DINOv3 ViT-L/16 (`facebook/dinov3-vitl16-pretrain-lvd1689m`) with a ViT-Adapter, an MSDeform pixel decoder, a Mask2Former head, and a refinement head on top. I want to be precise here because it's a common point of confusion: the larger \"H+\" variant (`dinov3-vith16plus`) shows up *only* as a commented-out fallback suggestion in the training config — it is not what's deployed. The deployed weights are the ViT-L/16 model, confirmed at `configs/phase1.yaml:13`.\n\n### The two model files, and why both must travel together\n\nThe model ships as two files baked directly into the container image. The first, `fence_dinov3_phase1.onnx`, is small — 13,902,638 bytes, about 13.3 MB. That's just the computation graph (the structure of the network). The second, `fence_dinov3_phase1.onnx.data`, is the giant — 2,451,570,688 bytes, roughly 2.28 GiB, which everyone rounds to \"2.45 GB.\" That file holds the actual learned weights. ONNX splits weights into an external file like this whenever a model exceeds the 2 GB protobuf limit, which this one does. I confirmed by scanning the graph that it references the external data file by name 1,696 times — one reference per weight tensor. The practical consequence: the two files are inseparable. ONNX Runtime resolves the `.data` path relative to wherever the `.onnx` file lives, so both have to sit in the same directory. The Dockerfile copies both into `/model/` (lines 40-41), and both deploy scripts refuse to even start a build unless both files are present in the build context. That 2.45 GB is also the number that dominates cold-start time, which I'll come back to.\n\n### The Dockerfile and the CUDA tightrope\n\nGetting onnxruntime-gpu to actually use the GPU (instead of silently falling back to CPU and running ~25x slower) is the single trickiest part of this whole subsystem, and the Dockerfile is built around solving it. The base image is `python:3.11-slim` — *not* an `nvidia/cuda` image. That's a deliberate call: the Cloud Run L4 host provides only the kernel-level GPU driver, and all the user-space CUDA libraries (cuBLAS, cuDNN, cuFFT, etc.) are pulled in instead as `nvidia-cu12-*` pip packages. This shaves about a gigabyte off the image and sidesteps pip's externally-managed-environment restriction that the nvidia base images impose.\n\nThe catch is that the dynamic linker has to be able to *find* those pip-bundled `.so` files, and it only reads `LD_LIBRARY_PATH` once, at process start. So the Dockerfile sets `LD_LIBRARY_PATH` as an `ENV` (line 30) pointing at all seven nvidia library directories *before* Python ever launches. The code comment is blunt about why: set it inside Python and you're too late, the linker won't re-read it, and CUDA will quietly fall back to CPU. As a second layer of insurance, `app.py` itself, at import time, explicitly `dlopen`s eight critical CUDA libraries (`libcudart.so.12`, `libcublas.so.12`, `libcublasLt.so.12`, `libcudnn.so.9`, `libcufft.so.11`, `libcurand.so.10`, `libnvJitLink.so.12`, `libnvrtc.so.12`) with `RTLD_GLOBAL` so their symbols are globally visible when ORT's CUDA provider loads. It also logs ORT's available providers at startup, which is the diagnostic you'd grep Cloud Logging for if you suspected a CPU fallback.\n\nThe dependency versions are pinned to match the Modal container and the training environment byte-for-byte: `onnxruntime-gpu==1.24.4`, `nvidia-cudnn-cu12==9.10.2.21`, plus pillow 10.4.0, numpy 1.26.4, fastapi 0.115.6, python-multipart 0.0.20, and uvicorn[standard] 0.32.0.\n\nOne more deliberate constraint: the container runs a *single* uvicorn worker (`--workers 1`). Multiple workers would each load their own copy of the 2.5 GB session into the L4's 24 GB of VRAM and you'd run out of room. Parallelism is handled at the Cloud Run service level via the concurrency setting instead.\n\n### The deploy command — the spec the client is paying for\n\nBoth `deploy.sh` (bash) and `deploy.ps1` (PowerShell) do the same thing; they're just two front doors for different operating systems. The flow is: `gcloud builds submit` to build the image in Cloud Build (with a 30-minute timeout because the ~2.5 GB build context upload is slow on the first run), then `gcloud run deploy` with the resource spec. That spec, line for line, is the most important thing for the cost discussion:\n\n- `--gpu 1 --gpu-type nvidia-l4` — one NVIDIA L4 GPU.\n- `--no-gpu-zonal-redundancy` — the cheaper, single-zone GPU allocation (zonal redundancy costs more and isn't needed here).\n- `--memory 16Gi --cpu 4` — 16 GiB RAM and 4 vCPUs on the CPU side.\n- `--concurrency 4` — one instance handles up to 4 requests at once.\n- `--min-instances 0 --max-instances 1` — this is the crux. Minimum zero means the service scales all the way down to *nothing* when idle (you pay nothing for compute while idle). Maximum one means there's a hard ceiling of a single instance.\n- `--region us-central1` — the canonical Cloud Run GPU region.\n- `--timeout 300s` — requests can run up to 5 minutes before Cloud Run kills them (generous, to survive cold starts).\n- `--execution-environment gen2` — the second-gen sandbox (required for GPU).\n- `--no-cpu-throttling` — CPU stays allocated even between requests (relevant for keeping a warm instance responsive).\n- `--allow-unauthenticated --port 8080` — public endpoint on port 8080.\n\nAfter deploy the script prints the service URL and reminds you to paste `<URL>/detect` into the JS client's `CONFIG.MODAL_ENDPOINT`.\n\n### Cold starts — the heart of the 24/7-warm question\n\nBecause `min-instances` is 0, the service genuinely turns itself off when nobody's using it. The upside is obvious: an idle simulator costs essentially nothing. The downside is the cold start. When a request arrives at a cold service, Cloud Run has to schedule and boot a fresh GPU instance, pull the (cached) image, start the container, initialize CUDA, and — the slow part — load that 2.45 GB of weights off the local filesystem into the L4's VRAM and build the ONNX session. In practice that adds up to roughly **30-60 seconds** before the first request gets an answer. Every subsequent request on that now-warm instance is fast (sub-second to a couple of seconds), because the session lives in a module-level global that's loaded exactly once in the FastAPI `lifespan` startup hook and reused. But once traffic stops and Cloud Run's idle window elapses, the instance is torn down and the very next visitor pays the full cold-start penalty all over again.\n\nThis is precisely the trade-off behind the client's \"should we keep it warm 24/7?\" question. Setting `min-instances 1` would pin one L4 instance alive around the clock, eliminating cold starts entirely — at the cost of paying for an idle GPU 24 hours a day, 7 days a week, whether or not anyone is using the simulator. The current configuration is the opposite end of that dial: pay nothing when idle, accept a 30-60s wait on the first hit after a quiet period. The model-baking decision reinforces this: the Dockerfile explicitly chose to bake the weights into the image rather than pull them from GCS at startup, precisely to keep the cold start as short as it is (pulling from GCS would add another 5-15s plus egress charges). The orchestrator now has the exact resource spec — 1x L4, 16 GiB, 4 vCPU, us-central1, gen2, no-zonal-redundancy — to price both the scale-to-zero status quo and the always-warm alternative.\n\n### Preprocessing parity — why the server output matches training\n\nA segmentation model is only as good as the consistency between how it was trained and how it's fed at inference. I checked this end to end and it lines up. The server resizes every upload to 512x512 using **bilinear** interpolation (the code comment explicitly warns against nearest-neighbor, which degrades small fences), divides by 255, then normalizes with the standard ImageNet mean `[0.485, 0.456, 0.406]` and std `[0.229, 0.224, 0.225]`, and arranges the tensor as NCHW `[1,3,512,512]` fp32. That matches the training image size (`configs/phase1.yaml:191`, image_size 512) and the export metadata (`tools/export_onnx.py`). On the output side, the model emits `(1,1,512,512)` sigmoid probabilities under the output name `mask_prob`. Crucially, temperature calibration is baked *into* the ONNX graph at export time (`sigmoid(logits / temperature)`), so the server does not — and must not — apply any extra calibration; it just scales the probabilities to 0-255 and PNG-encodes them. The 1/255 quantization is about 0.4% error, well under any threshold the browser applies.\n\n### Relationship to the Modal version\n\nThis Cloud Run service is a near-exact sibling of `modal_inference/app_dinov3.py`. Same two endpoints, same CORS allow-list, same preprocessing, same model files. The differences are purely the hosting substrate: Modal uses its own decorators, a T4 GPU, and `scaledown_window=600` with `max_containers=4`; Cloud Run uses a Dockerfile, an L4 GPU, FastAPI's `lifespan` hook, and the `max-instances 1` cap. The Cloud Run copy exists because Cloud Run wants a plain ASGI app and a container image rather than Modal's framework. For the client report, the takeaway is that Cloud Run on the L4 is the *current* production host, and the architecture was lifted directly from the proven Modal implementation.

## UNCERTAINTIES
- The ~30-60s cold-start figure is stated in the app.py/Dockerfile design comments and is consistent with loading 2.45 GB into VRAM, but I did not observe a live cold start or find a measured benchmark in this directory. The exact cold-start latency should be confirmed against Cloud Run logs / the X-Inference-Ms header on a real first request if precision matters for the report.
- No pricing numbers exist anywhere in cloudrun_inference/ — the directory only defines the resource spec (1x L4, 16Gi, 4 vCPU, us-central1, no-zonal-redundancy, gen2). Actual USD costs for scale-to-zero vs 24/7-warm must be computed by the orchestrator from current GCP Cloud Run GPU pricing.
- Cloud Run's idle scaledown window (how long an instance stays warm before being torn down) is NOT configured in deploy.sh/deploy.ps1, so it uses the Cloud Run default. The Modal sibling uses scaledown_window=600 (10 min); the Cloud Run default differs and is not pinned here. Worth confirming the effective Cloud Run idle timeout if the report discusses how often cold starts recur.
- deploy.ps1:18 says '~14 MB graph' while deploy.sh:16 says '~13 MB'; the actual graph file is 13.9 MB. Minor doc rounding inconsistency, not a functional issue.
- I could not independently confirm that the .onnx/.onnx.data files in cloudrun_inference/ are byte-identical to the canonical copies under ../models/ (they are expected to be copied from there per the deploy scripts), though sizes and the DINOv3 ViT-L/16 lineage are consistent.
- phase1.yaml contains several 'rolled back from X' comments where the value equals X (e.g. multi_block_n: 6 'rolled back from 6', pixel_decoder_layers: 12 'rolled back from 12'), suggesting the comments may be stale relative to the actual values. This affects the model-architecture description, not the Cloud Run hosting spec, but flagging it for whoever audits the model config.
